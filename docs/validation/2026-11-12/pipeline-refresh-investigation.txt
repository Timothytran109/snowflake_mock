Demonstrated component defect and scoped fix
- Provider 2.4.0's async get_sync_status_async() delegates with
  always_wait_when_syncing=False. With a newer succeeded_at AND sync_state=syncing,
  the real installed provider reports success in a mocked reproduction. Its
  synchronous initial completion check uses always_wait_when_syncing=True.
- The previous callback trusted status=success without reconciling the current
  connector state or retaining its pre-sync completion watermark. This allows
  premature release under concurrent/rescheduled ingestion. It is a demonstrated
  code-level gap, NOT a proven explanation of the particular PAY_1000 incident.
- The guarded operator now captures the provider's existing watermark in _sync(),
  persists it in TaskDeferred callback kwargs, and rechecks completion after both
  immediate and asynchronous provider success. Current destination/connector
  guards run again; success must be strictly newer than the watermark, the
  connector must be idle/scheduled, no newer failure can supersede the success,
  and any reported completion must be valid and visible in current metadata.
- Missing/stale/inflight/rescheduled/inconsistent results fail closed using the
  existing retry policy; a retry can issue another force request. This preserves
  the provider, deferred trigger, timeout, credentials and four-task ordering.
- Safe logs now capture the provider watermark/completion, exact dbt argv/cwd/
  profile/target and each model's destination, numeric adapter count and execution
  times. No environment dump, profile contents, full API/adapter payload, raw
  dbt output or private-key contents are logged. View DDL counts are not source
  row counts, and no per-payment freshness guarantee is inferred from them.
